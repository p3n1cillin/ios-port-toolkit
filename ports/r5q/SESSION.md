Decisive correlation: every test that performed the MMU-off → loader_return_stub → MMU-on round trip hung (15, 16, 18); every test that avoided it returned (5/9/13 = R5Q_PREPARE_ONLY "handoff not attempted"; 17 = firmware PS_HOLD, no stub). So the fault is in that sequence, not the hypervisor (already cleared).

Mechanism hypothesis: loader_return_stub reads loader_ctx[] (TTBR0/TCR/MAIR/VBAR/CPACR/SP/SCTLR) with the MMU+D-cache OFF (non-cacheable), so loader_ctx must be at PoC before the jump. loader_save_ctx writes it with caches on. Pre-jump cleaning covers the firmware map (types 1-6/9/10), the stack (sp±0x2000) and the kernel image (phys_base..top) — but loader_ctx is a loader global, cleaned explicitly only on the multi-core run_on_other_cpu path. On the single-core lab path (cpus=1, direct jump_to_kernel) it reaches PoC only if the firmware map reports the loader image as a cleanable type, which is not guaranteed on the phone. Stale loader_ctx → stub restores bad TTBR0/SCTLR → MMU-enable faults/hangs. Invisible to Unicorn (no cache) and QEMU TCG (coherent).

Fix: loader.c R5Q_EXPLICIT_CTX_CLEAN flushes (civac) loader_ctx + the stack frame to PoC right before the jump, independent of the map loop. Behind #ifdef; Test 18 rebuilds byte-identical. Test 29 = Test 18 + this flag (build-test29.sh, --test29). 11 shim + 4 roundtrip cases PASS; the '[LAB] ctx+stack flushed to PoC (explicit)' tag is present; full return verified.
